# Firestore Members Security Model

## Purpose

Phase 5C prepares the remote member model and security rules before any
confirmed Excel import can write real members to Firestore.

This phase does not write final members. It defines the safe paths, role
boundaries, and tests that Phase 5D must keep passing.

## Remote Member Public Doc

Path:

```txt
groups/{groupId}/members/{memberId}
```

Allowed fields:

```txt
firstName
lastName
fullName
gender?
joinedAt?
groupRole?
semesterAttendances?
isServer?
isServing?
status?
documentIdHash?
importedFrom?
lastImportRunId?
lastImportedAt?
createdAt
updatedAt
```

The public member doc is intended for group operational views. It must not
store the full `documentId`, phone, birthday, pastoral notes, or other private
profile data.

Current viewer decision:

- Active `viewer` memberships may read public member docs.
- This is acceptable only while the public doc excludes full document ids and
  other sensitive fields.
- `documentIdHash` is still technical metadata and should not be displayed in
  UI. Revisit whether viewers should read it before broad production use.

## Private Profile

Path:

```txt
groups/{groupId}/members/{memberId}/private/profile
```

Allowed fields:

```txt
documentId?
phone?
birthday?
createdAt
updatedAt
```

The full `documentId`, if stored, belongs only here. Active `owner` and
`leader` memberships can read/write this document. `viewer`, inactive members,
signed-out users, and users without membership cannot read or write it.

## documentIdHash

`documentIdHash` is the deduplication key used by import preview and future
confirmed writes. It allows technical matching without storing the raw document
number in preview rows or public import logs.

Rules:

- Do not show `documentIdHash` in UI.
- Do not log raw `documentId`.
- Store full `documentId` only in `private/profile` if the product explicitly
  needs it.
- Future duplicate detection must keep hash generation consistent between
  preview and confirmed write.

## importRuns And previewRows

Paths:

```txt
groups/{groupId}/importRuns/{importRunId}
groups/{groupId}/importRuns/{importRunId}/previewRows/{rowId}
```

Client rules:

- Active `owner` and `leader` can create and read importRuns.
- `viewer`, inactive, signed-out, and unaffiliated users cannot create
  importRuns.
- Clients cannot update importRuns after creation.
- Clients cannot write previewRows. Cloud Functions/Admin SDK writes preview
  rows because Admin SDK bypasses Security Rules.
- Active `owner` and `leader` can read previewRows.
- `viewer` cannot read previewRows because preview data may expose operational
  import details and document hash metadata.

## Storage Uploads

Path:

```txt
imports/{groupId}/{importRunId}/source.xlsx
```

Storage Rules allow only active `owner` or `leader` memberships to upload or
read the source XLSX. `viewer`, inactive, signed-out, and unaffiliated users are
denied. Uploads are limited to 20 MB and XLSX-compatible content types.

Client overwrite and delete are denied.

## Roles

- `owner`: can manage memberships, create/read importRuns, read previewRows,
  create/update public member docs, and read/write private profiles.
- `leader`: can create/read importRuns, read previewRows, create/update public
  member docs, and read/write private profiles.
- `viewer`: can read group and public member docs only. Cannot import, write
  members, read private profiles, or read previewRows.
- `inactive`: denied for group, import, member, private profile, and upload
  access.

## Before Final Writes

Phase 5D must keep these gates:

- `pnpm test:rules` passing.
- `pnpm test:storage-rules` passing.
- Destination group selected.
- Active `owner` or `leader` membership.
- Preview generated by backend.
- Explicit confirmation before writing final members.

## Risks Pending

- Last-owner protection is still not implemented. Use a controlled
  transactional backend path or owner-count design before advanced role
  administration.
- Viewer access to public member docs depends on keeping sensitive fields out
  of that document. Firestore Rules cannot hide individual fields from a
  readable document.
- Storage source file retention/deletion policy is still pending.
- Membership mirrors must stay synchronized with authoritative memberships.
- Rules must be re-tested whenever new remote collections or permissions are
  added.
- Meetings, attendance, and pastoral notes are still not covered by final
  remote rules/tests because they are not migrated yet.
